## 🔴 КРИТИЧЕСКИЕ МОМЕНТЫ МАКСИМАЛЬНОЙ НАГРУЗКИ

### 1. **Еженедельный раунд мэтчинга** (ПИКОВАЯ НАГРУЗКА)
**Когда**: По расписанию (по умолчанию пятница, 12:00 МСК)

**Что происходит**:
- Загрузка всех кандидатов из БД (до 5000 пользователей)
- Построение всех возможных пар: **O(n²) = до 12,500,000 пар** (5000 × 4999 / 2)
- Вычисление коэффициента Жаккара для каждой пары
- Жадный алгоритм выбора пар
- Сохранение мэтчей в БД
- **Массовая отправка уведомлений** (до 5000 сообщений одновременно)

**Нагрузка**:
- **CPU**: Высокая (вычисление Jaccard для миллионов пар)
- **RAM**: Высокая (хранение всех кандидатов и рёбер в памяти)
- **БД**: Очень высокая (множественные SELECT, INSERT, UPDATE)
- **Telegram API**: Критическая (до 5000 запросов `send_message` + `send_media_group`)

**Время выполнения**: 
- При 5000 пользователях: **5-15 минут** (зависит от сервера)
- При 1000 пользователях: ~1-2 минуты

**Узкие места**:
```python
# round.py:198-244 - Построение всех рёбер
for idx, user_a in enumerate(candidates):  # O(n)
    for user_b in candidates[idx + 1:]:   # O(n²)
        jaccard = compute_jaccard(...)      # O(interests)
```

**Рекомендации**:
- ⚠️ **КРИТИЧНО**: Использовать батчинг для отправки сообщений (не более 30 сообщений/сек)
- Добавить rate limiting для Telegram API
- Рассмотреть предварительное вычисление Jaccard в фоне
- Использовать пул соединений к БД (минимум 10-20 соединений)

## 🆕 ДОПОЛНИТЕЛЬНЫЕ КРИТИЧЕСКИЕ ПРОБЛЕМЫ (2026-01-22)

### 7. **Отсутствие Connection Pooling для БД** (КРИТИЧНО!)
**Файл**: `app/database/db.py:38-43`

**Проблема**:
```python
def make_engine(settings: Settings):
    return create_async_engine(
        settings.db_url,
        echo=False,
        future=True,
        pool_pre_ping=True,
    )
```

**Что не так**:
- НЕ настроен `pool_size` и `max_overflow`
- SQLAlchemy по умолчанию использует pool_size=**5**, max_overflow=**10**
- **Максимум 15 одновременных соединений** к БД!
- При 5000 пользователях и пиковой нагрузке это приведет к блокировкам

**Нагрузка**:
- **Во время раунда мэтчинга**: тысячи запросов конкурируют за 5-15 соединений
- **Timeout ошибки** и **Queue Full** при превышении лимита
- **Деградация производительности** на 80-90%

**Рекомендации**:
- ⚠️ **КРИТИЧНО**: Установить `pool_size=50`, `max_overflow=100` для PostgreSQL
- Для SQLite connection pooling бесполезен (один writer)
- Добавить мониторинг pool utilization

**Пример исправления**:
```python
def make_engine(settings: Settings):
    pool_config = {}
    if "postgresql" in settings.db_url:
        pool_config = {
            "pool_size": 50,
            "max_overflow": 100,
            "pool_timeout": 30,
            "pool_recycle": 3600,
        }
    return create_async_engine(
        settings.db_url,
        echo=False,
        future=True,
        pool_pre_ping=True,
        **pool_config,
    )
```

### 8. **Множественные flush() в цикле создания мэтчей** (ВЫСОКАЯ НАГРУЗКА)
**Файл**: `app/services/matching/round.py:289-306`

**Проблема**:
```python
async def _persist_matches(...):
    created: list[Match] = []
    for edge in pairs:  # До 2500 итераций!
        match = Match(...)
        session.add(match)
        user_a.last_pairing_at = now
        user_b.last_pairing_at = now
        await session.flush()  # ❌ FLUSH ПОСЛЕ КАЖДОГО МЭТЧА!
        created.append(match)
    return created
```

**Что не так**:
- При 2500 мэтчах = **2500 операций flush()**
- Каждый flush() = round-trip к БД
- Вместо batch insert делается 2500 отдельных вставок

**Нагрузка**:
- **БД**: Критическая (2500 транзакций вместо 1)
- **Время выполнения**: +5-10 секунд только на flush
- **Lock contention** на таблице matches

**Рекомендации**:
- Удалить `flush()` из цикла
- Сделать один `flush()` после цикла
- Использовать bulk insert для больших батчей

**Пример исправления**:
```python
async def _persist_matches(...):
    created: list[Match] = []
    for edge in pairs:
        match = Match(...)
        session.add(match)
        user_a.last_pairing_at = now
        user_b.last_pairing_at = now
        created.append(match)
    
    await session.flush()  # ✅ Один flush для всех мэтчей
    return created
```

### 10. **Отсутствие rate limiting при отправке сообщений** (КРИТИЧНО!)
**Файлы**: 
- `app/services/matching/round.py:309-331` (уведомления о мэтчах)
- `app/services/matching/feedback.py:52-73` (обратная связь)
- `app/services/matching/messages.py:256-270` (_broadcast)

**Проблема**:
```python
# round.py:325-330
for match in matches:  # До 2500 мэтчей
    await _send_match_invite(..., is_user_a=True)   # Без задержки
    await _send_match_invite(..., is_user_a=False)  # Без задержки

# feedback.py:58-73
for user in (match.user_a, match.user_b):
    await bot.send_message(...)  # Без rate limiting
```

**Что не так**:
- **НЕТ rate limiting** для Telegram API
- Telegram лимит: **30 сообщений/сек**
- При превышении: FloodWait ошибка на **несколько часов**

**Нагрузка**:
- **Telegram API**: Критическая
- При 5000 сообщений подряд: **FloodWait на 2-3 часа**
- Бот перестанет отвечать всем пользователям

**Рекомендации**:
- ⚠️ **КРИТИЧНО**: Реализовать очередь с rate limiter (30 msg/sec)
- Использовать `asyncio.Semaphore` + `asyncio.sleep`
- Добавить retry с экспоненциальной задержкой

**Пример исправления**:
```python
import asyncio

# Глобальный семафор для rate limiting
_telegram_semaphore = asyncio.Semaphore(30)  # 30 запросов одновременно
_last_send_time = 0

async def send_with_rate_limit(bot, chat_id, text, **kwargs):
    global _last_send_time
    async with _telegram_semaphore:
        # Гарантируем не более 30 сообщений/сек
        now = asyncio.get_event_loop().time()
        elapsed = now - _last_send_time
        if elapsed < 1.0 / 30:
            await asyncio.sleep(1.0 / 30 - elapsed)
        result = await bot.send_message(chat_id, text, **kwargs)
        _last_send_time = asyncio.get_event_loop().time()
        return result
```

### 13. **Отсутствие индексов на критических полях** (ВЫСОКАЯ НАГРУЗКА БД)
**Файл**: `app/database/models.py:276-316`

**Проблема**:
```python
class Match(Base):
    # ...
    status: Mapped[str] = mapped_column(String(16), default="pending_response", index=True)
    # ❌ Нет составных индексов!
    notified_a: Mapped[bool] = mapped_column(default=False, index=True)
    notified_b: Mapped[bool] = mapped_column(default=False, index=True)
```

**Что не так**:
- Запросы часто фильтруют по `(status, created_at)` одновременно
- Запросы ищут `(status == X) AND (notified_a == False OR notified_b == False)`
- Отдельные индексы менее эффективны, чем составные

**Нагрузка**:
- **БД**: При 10,000 мэтчей каждый SELECT сканирует таблицу
- **Время**: +200-500ms на каждый запрос

**Рекомендации**:
- ⚠️ **ВАЖНО**: Добавить составные индексы:
  - `CREATE INDEX idx_matches_status_created ON matches(status, created_at)`
  - `CREATE INDEX idx_matches_pending_notified ON matches(status, notified_a, notified_b) WHERE status = 'pending_response'`

### 14. **SQLite вместо PostgreSQL** (БЛОКИРУЮЩАЯ ПРОБЛЕМА!)
**Файл**: `app/services/core/config.py:153`

**Проблема**:
```python
db_url = os.getenv("DATABASE_URL", "sqlite+aiosqlite:///data/db.sqlite3")
```

**Что не так**:
- SQLite по умолчанию (если не задан DATABASE_URL)
- SQLite имеет **один writer** - все записи последовательны
- При раунде мэтчинга: 2500 INSERT + 5000 UPDATE = **блокировка на минуты**
- Connection pooling бесполезен для SQLite

**Нагрузка**:
- **БД**: Полная блокировка при записи
- **Время**: Раунд мэтчинга займет **30-60 минут** вместо 5-10
- **Ошибки**: Database is locked

**Рекомендации**:
- ⚠️ **КРИТИЧНО**: Перейти на PostgreSQL для прода
- SQLite допустим только для dev (<100 пользователей)

### 15. **Обработка таймаутов загружает ВСЕ активные мэтчи** (СРЕДНЯЯ НАГРУЗКА)
**Файл**: `app/services/matching/jobs.py:95-104`

**Проблема**:
```python
stmt = (
    select(Match)
    .options(selectinload(Match.user_a), selectinload(Match.user_b))
    .where(Match.status.in_(stage_map.keys()))
)
result = await session.execute(stmt)
matches = list(result.scalars().all())  # Загружаем ВСЕ в память

for match in matches:  # До 2500 итераций
    # Обработка каждого мэтча
```

**Что не так**:
- Загружаются **ВСЕ** мэтчи со статусом `pending_response`
- При 2500 активных мэтчах: **весь набор в памяти**
- Eager loading (`selectinload`) делает доп. запросы

**Нагрузка**:
- **БД**: 2-3 SELECT запроса (matches + users)
- **RAM**: ~5-10 MB для 2500 мэтчей с relations
- **Время**: Выполняется каждые 5-30 минут

**Рекомендации**:
- Фильтровать в SQL по времени (например, created_at > NOW() - timeout)
- Использовать пагинацию (LIMIT + OFFSET)
- Обрабатывать батчами по 100-500 мэтчей
