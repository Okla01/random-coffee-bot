Ты работаешь в репозитории Telegram-бота на aiogram v3 (асинхронный SQLAlchemy, структура примерно app/handlers, app/services, app/database/models.py и т.д.).

Нужно реализовать функционал еженедельного подбора собеседников ("matching") по подробностям ниже. Очень важно: бизнес-логика живет в app/services/*, а handlers только принимают Telegram-события, вызывают сервисы и отправляют сообщения.

---

1. ОБЩИЕ ПРАВИЛА

- Пользователь участвует в подборе, если у него:
  - user.status == "active"
  - user.stage == "profile_filled"
- При редактировании анкеты (любой prof:edit:*) user.status должен становиться "not_active" до следующего успешного prof:save.
- Отдельная кнопка "Участвовать в подборе" (prof:join) по смыслу больше не нужна, participation определяется статусом active.
- Отписаться от подбора нельзя (кроме удаления анкеты или блокировки админом).

- Импорт пользователей из excel ("origin == 'import'", "import_payload") больше не используется:
  - Удали/закомментируй соответствующие ветки логики в services/onboarding.py и services/profile/editing.py.
  - Сами поля origin/import_payload в модели User пока не трогай (оставь для совместимости, но не используй в коде).

2.1. User

2.2. Match

- В app/database/models.py расширь модель Match:

  Сейчас:

    class Match(Base):
        id
        user_a_id
        user_b_id
        created_at
        status
        user_a, user_b
        UniqueConstraint(user_a_id, user_b_id)

  Нужно:

  - УБРАТЬ UniqueConstraint("user_a_id", "user_b_id", name="uq_match_users") (появится несколько записей для одной пары в разных раундах).
  - Добавить поля (тип можно подобрать по месту — String/Float/JSON/DateTime):

    - score: float | None           # Jaccard для пары
    - round_id: str | None          # идентификатор раунда (например "2025-11-28T12:00Z" или "2025-W48")
    - a_response: str               # "none" | "accept" | "skip"
    - b_response: str
    - a_response_at: datetime | None
    - b_response_at: datetime | None
    - slots_json: JSON | None       # слоты календаря (оба пользователя + пересечение)
    - meeting_at: datetime | None   # итоговое время встречи в UTC
    - meeting_tz: str | None        # удобный TZ для отображения
    - cancel_reason: str | None     # причина отмены (если была)
    - cancelled_by_user_id: int | None

  - Расширь семантику поля status (строка, как сейчас), но не меняя тип:
    Возможные значения:
      - "pending_responses"
      - "cancelled_skip"
      - "cancelled_timeout"
      - "calendar_pending"
      - "calendar_no_slots"
      - "meeting_proposed"
      - "meeting_scheduled"
      - "cancelled_after_confirm"
      - "cancelled_admin"
      - "cancelled_deleted"
      - "completed"

  Важно: Не отправляй сообщения из модели, только описывай поля.

  - matching_enabled и last_matching_round_at попадали в dict текущих настроек;

- last_matching_round_at будет использоваться только сервисом подбора (см. ниже), из админки его можно пока просто отображать или вообще не трогать.

3. СЕРВИС ПОДБОРА (app/services/matching/engine.py)

Создай модуль app/services/matching/engine.py со следующей идеей:

- В нём НЕТ Telegram-кода. Только бизнес-логика и работа с БД.
- Опиши внешнее API (пример):

  async def run_matching_round(session_factory: async_sessionmaker[AsyncSession]) -> MatchingRoundResult: ...

  где MatchingRoundResult — dataclass со списком созданных матчей / пар (чтобы handlers могли разослать сообщения).

Алгоритм run_matching_round:

1) Считать настройки из таблицы Setting:

   - matching_enabled
   - min_jaccard
   - cooldown_weeks
   - match_day
   - match_utc_hour
   - last_matching_round_at

   Если matching_enabled != "1" — сразу выйти.

   Проверить, что текущий момент (UTC) совпадает с match_day + match_utc_hour. Если нет — выйти.
   Использовать last_matching_round_at как защиту от повторного запуска:
   - если там уже записан раунд с тем же днём/часом (условно "та же пятница 12:00 UTC"), не запускать подбор второй раз.

2) Сформировать пул кандидатов (список User):

   - user.status == "active"
   - user.stage == "profile_filled"
   - interests_json не NULL и список не пуст
   - (опционально) есть хотя бы одно фото в photos_json
   - НЕТ активных матчей для этого пользователя:
     - Match с этим user (как user_a или user_b) и status в:
       ["pending_responses", "calendar_pending", "meeting_proposed", "meeting_scheduled"].
   - cooldown:
     - last_match_at is NULL
       ИЛИ now >= last_match_at + cooldown_weeks * 7 дней.

3) Рассчитать Jaccard-метрику для всех пар кандидатов:

   - Для каждого пользователя построить множество интересов:
       interests = {строки из interests_json["interests"] в нижнем регистре без пробелов по краям}.
   - Для пары (i, j):
       union = A ∪ B
       inter = A ∩ B
       если union пустое — считаем jaccard = 0
       иначе jaccard = len(inter) / len(union)
   - Оставить пары, где jaccard >= min_jaccard.

4) Учитывать историю матчей:

   - Получить из БД историю матчей между парами пользователей.
   - Разделить все пары на:
     - новые: у которых ещё нет Match (любой статус) между этими двумя user_id;
     - старые: у которых уже есть хотя бы один Match.
   - Жадный выбор:
     - сначала сортировать НОВЫЕ пары по score по убыванию, пройтись и выбирать пары, не включая пользователя более одного раза в раунд;
     - затем, если ещё остались свободные пользователи и есть СТАРЫЕ пары, можно по тому же принципу добрать старых пар, пока это имеет смысл.
   - В итоге всегда один пользователь в одной паре за раунд. Пока хватает новых комбинаций, пары не повторяются.

5) Для каждой выбранной пары создать Match:

   - user_a_id, user_b_id (упорядочи по id, чтобы не было разницы, кто A, кто B).
   - created_at = now
   - round_id = строка с идентификатором раунда (например, текущий момент в ISO или "2025-W48")
   - status = "pending_responses"
   - score = jaccard
   - a_response = "none", b_response = "none"
   - a_response_at/b_response_at = None
   - slots_json = None
   - meeting_at = None, meeting_tz = None
   - cancel_reason = None, cancelled_by_user_id = None
   - Обновить user.last_match_at = now для обоих.

6) Обновить Setting["last_matching_round_at"] = now (в ISO-формате).

7) Вернуть MatchingRoundResult c информацией о созданных матчах (id матчей и пары user_id), чтобы handlers могли отправить сообщения.

4. ХЕНДЛЕРЫ MATCHING (app/handlers/matching.py)

Создай новый модуль handlers/matching.py и router.

Нужно:

4.1. Отправка анкет после раунда

- Существующий код APS-scheduler (там, где будет вызываться run_matching_round) должен после вызова сервиса:
  - пройтись по созданным матчам и отправить каждому участнику анкету другого:
    - все фото из photos_json
    - текст (name, age, bio, interests)
    - inline-клавиатуру:
      [Готов познакомиться]  → callback_data="match:resp:{match_id}:accept"
      [Пропустить на этой неделе] → callback_data="match:resp:{match_id}:skip"

 Handler-у достаточно иметь хендлер callback_query для префикса "match:resp:".

4.2. Обработка реакции "Готов/Пропустить"

- В handlers/matching.py:
  - callback_query-хендлер, который:
    - по match_id и текущему пользователю понимает, он user_a или user_b.
    - делегирует бизнес-логику в сервис, например:

      async def process_match_response(
          session: AsyncSession,
          match: Match,
          current_user: User,
          action: Literal["accept", "skip"],
      ) -> MatchResponseResult

      где MatchResponseResult описывает:
        - новое состояние матча
        - нужно ли уведомить вторую сторону и каким текстом
        - нужно ли запускать сценарий выбора времени

    - Handler уже на основе результата:
      - редактирует/отправляет сообщения пользователям;
      - при обоих "accept" запускает диалог выбора времени.

4.3. Календарь и выбор слотов

- Реализуй в services/matching/calendar.py (или внутри engine.py, но лучше отдельный модуль) логику работы со слотами:

  - функции для сохранения слотов пользователя в Match.slots_json,
  - расчёта пересечения,
  - перевода в UTC и обратно с учетом User.tz.

- В handlers/matching.py сделай обёртки-диалоги (aiogram-dialog) для:
  - выбор даты + временного диапазона пользователем;
  - вызов сервисов, которые:
    - при выборе слотов для первого/второго пользователя обновляют slots_json;
    - при наличии слотов обеих сторон считают пересечение и переводят матч в status="meeting_proposed" + возвращают текст для сообщения.
  - callbackи для "Подтвердить"/"Назначить заново":
    - "Подтвердить": при подтверждении обоих → status="meeting_scheduled", заполнить meeting_at/meeting_tz.
    - "Назначить заново": очистить слоты соответствующего пользователя, вернуть статус в "calendar_pending" и запустить выбор слотов заново.

4.4. Команда /matching

- Добавь в handlers/matching.py команду /matching:
  - находит активный матч пользователя в статусе "meeting_scheduled";
  - показывает:
    - анкету пары,
    - дату и время встречи,
    - статус,
    - inline-кнопки: [Отменить встречу] [Всё в силе].

- Callback для "Отменить встречу":
  - уточнение [Да/Нет];
  - при "Да":
    - запрос текстовой причины,
    - сервис, который:
      - ставит status="cancelled_after_confirm",
      - заполняет cancel_reason и cancelled_by_user_id,
      - уведомляет партнёра.
